# Gate verification lifecycle (decision-bound human gates)

**Answer first.** A decision-bound human gate (a `human:*` ticket whose description declares `DECISION OPTIONS:`) closes only on a signed, single-use decision token. A token answers one ticket, one workflow and one review cycle. If the gate also carries a `postCondition`, an approved close is **held**: the gate stays In Review behind `gate:verifying` until the post-condition is observed. If the window ends first, the gate is marked `gate:approved-unverified` and the human is paged again. Nothing downstream unblocks while a gate is held. Every item of state below has one writer per twin, a defined reader, and a defined end of life. Both ticket twins (`lambda/agentcore-hub-tickets`, DynamoDB; `lambda/agentcore-hub-jira`, Jira) implement the same rules from the shared, byte-identical `gate-contract.mjs` and `decision-contract.mjs` (pinned by `scripts/check-fix-kinds-parity.sh`). The orchestrator owns none of this (DL-009).

Added by TEAM-5338 (review round 1 on TEAM-5315). Related: DL-028 (conditional deploy gate) in `docs/architecture.md`.

## Lifecycle of one gate

1. **Create.** `create_issue` / `create_ticket` with `post_condition` (needs `human:*` and a `DECISION OPTIONS:` line).
2. **Decide.** The human picks an option in the hub console (the hub mints a token, only for a verified human, see [Who may decide](#who-may-decide)) or on Telegram (the bridge mints its own). The route forwards the token to `Tickets___transition_ticket`.
3. **Resolve.** `resolveDecision` (gate-contract) verifies the HMAC, ticket, workflow, expiry, the cycle cut-off (`notBeforeMs`) and that the jti is unspent.
4. **Spend + close or hold.** The jti is recorded as spent. With no post-condition, or one that is already met, the gate goes Done. Otherwise it is held: `gate:verifying` + a signed `gateVerify` record (`verifyUntil` = now + `VERIFY_WINDOW_MS`, 10 min).
5. **Reprobe** (`{mode:"reprobe"}`, EventBridge every 2 min). Each held gate is checked against the signed record. **Met:** the gate goes Done and the record is deleted. **Window over and still unmet:** `gate:verifying` is swapped for `gate:approved-unverified`, the human is paged again, and the record is deleted.
6. **Reopen.** Any non-Done move out of In Review/Done (request changes, `blocked_by` park) starts a new cycle. Every earlier token and DECISION comment becomes stale, and the hold state is cleared.

## Who may decide

`src/lib/auth/human.ts` `requireHumanIdentity(req)` is the single answer. It is used by every hub route that mints a decision token or clears a DL-035 park. It refuses:

- `unauthenticated`: auth is on and there are no identity headers.
- `default_identity`: `AUTH_MODE=none`, where every caller (agents with `http_request`/`shell` included) is `default` and headers are untrusted; or the user is literally `default`.
- `service_identity`: `svc:*`.

| Route | Non-human caller | Human caller |
|---|---|---|
| `POST /api/workflow/[id]/tickets/transition` with `decision` and no `decisionToken` | 403 `{reason:"decision_required", detail:"decision_channel_unavailable", identity:<reason>}`, nothing invoked | Token minted with `by = email \|\| userId` |
| same, with a bridge-presented `decisionToken` | Forwarded verbatim. The Telegram bridge is the human channel, and the only one under `AUTH_MODE=none`. | same |
| `POST /api/workflow/[id]/retry` on a **parked** ticket | 403 `{error:"human_identity_required", reason, ticketId}`, no lease/park/status write | Un-parks, then readies |
| `POST /api/workflow/[id]/nudge` `{ticketId}` on a **parked** ticket (dynamodb + jira) | 403, same body, no write | Un-parks, then dispatches |
| retry / targeted nudge on an **unparked** ticket, untargeted nudge | Unchanged (open) | Unchanged |

Consequence: the Workflow Manager (`deploy/workflow-manager/toolkit/intervene.py`) can no longer un-park. `retry` / `dispatch` / `unstick --ticket` on a parked ticket exit with `REFUSED (human identity required)`, and its system prompt tells it to `escalate`.

## Contract change for the frontend ticket (held response)

`POST /api/workflow/[id]/tickets/transition` now returns a distinct 200 body when the twin holds an approved close (type `TransitionHeldResponse`, `src/lib/workflow/decision-grammar.ts`, re-exported from `decision-contract.ts`):

```json
{ "success": true, "held": true, "status": "verifying", "ticketId": "TEAM-G", "targetStatus": "done",
  "newStatus": "in_review", "verifyUntil": "2026-10-06T12:30:00.000Z",
  "postCondition": { "met": false, "detail": "lambda_version: want 7, have 6" },
  "decision": "continue", "completionRecordWritten": true }
```

`decision` appears only when a decision was picked; `completionRecordWritten` only when `evidence` was sent. Every other success keeps the old shape (`{success, ticketId, newStatus: targetStatus, …}`).

**Frontend follow-up — done (TEAM-5339).** `src/components/workflow/TicketDetailModal.tsx` now parses the response through `src/lib/workflow/transition-result.ts` (`parseTransitionResponse`) instead of repainting `targetStatus` on any `res.ok`: a held response keeps the ticket `in_review` and shows "Approval held — verifying post-condition…" with `postCondition.detail`; the ticket's own `gate:verifying` / `gate:approved-unverified` labels (`gateHoldState`) drive the same banners on load, so reopening the modal never shows stale state, and an approved-unverified gate re-pages through the existing decision picker (Approve relabelled "Override (unverified)"). Still open: the 403 refusal still shows the same "service" notice regardless of `identity` — `detail === "decision_channel_unavailable"` + `identity: "unauthenticated"` / `"default_identity"` should instead say "sign in through SSO or use Telegram". The Telegram bridge (`deploy/telegram-bug-intake/index.mjs`, gate ✅ and DECISION callbacks) already branches on `status === "verifying"`.

## Residual risks (accepted, bounded)

- **R1: Jira jti window (no CAS).** Jira issue properties have no conditional write. Two closes presenting one token within the read-check-put window of `recordJti` can both pass. Bounds: the same human chose the same option; the 15-minute token TTL; the cycle cut-off; the jti is put **before** the transition. The DDB twin is atomic.
- **R2: direct table/property writes.** The guarantees assume the only writers are the twins' Lambda roles. A principal with direct `dynamodb:UpdateItem` on the tickets table, or Jira admin credentials, could strip `decisionJtisUsed` or the `gateCycleResetAt` stamp. It still cannot forge a token or a `gateVerify` signature (the HMAC key is in Secrets Manager). The fleet is meant to reach tickets only through the `Tickets___*` tools (`TICKET_TOOLS_LAMBDA`). Any runtime or operator role that also holds direct write on the tickets table sits inside this residual, and should be audited in the follow-up IAM review.
- **R3: `/myself` down → reopen cost** (`src/app/api/jira/webhook/route.ts`). When the service account cannot be resolved, a human Jira-UI Done on a bound gate is not ratified. It is reopened and paged again (throttled to once per gate per 10 min, per ECS task). A real human approval made in the Jira UI during an outage therefore costs one more click.
- **R4: unbound gate passes through on `/myself` failure.** A gate whose description was read and **declares no options** still forwards Done while `/myself` is down. It binds no decision, so nothing is approved by guess. An unreadable description is not "unbound" and fails closed.
- **R5: rollout.** Tokens without a jti, and `gateVerify` v1 records still in flight at deploy, fail closed (`token_malformed` / `ignored_unsigned`). The human decides again: at most one extra click per in-flight gate.

## Out-of-scope follow-ups (tracked, not fixed here)

1. **Reconcile sweep can advance an un-forwarded Jira Done** (orchestrator change, DL-009 scope). When the webhook refuses to forward a Done but the issue stays Done in Jira (e.g. the reopen failed with a 503), then in Jira mode `getChildTickets` (`lambda/orchestrator/index.mjs`, `getChildTicketsFromJira`) feeds `allBlockersResolved` / `reconcileDependent` (`lambda/orchestrator/reconcile-sweep.mjs`) live Jira statuses. After the lease TTL in enforce mode, that can re-drive dependents. Fix: the sweep should treat a decision-bound gate's Done as resolved only with the twin's ratification.
2. **`POST /api/workflow/cd-registry` has no identity check** (`src/app/api/workflow/cd-registry/route.ts`). Registry write equals deploy-trigger authority (see CLAUDE.md, "CD registry"). It should use `requireHumanIdentity` + admin.
3. **`isAdmin()` is true under `AUTH_MODE=none`** (`src/lib/auth/identity.ts`). Agents reaching the hub are therefore "admin" for the cloud-code GitHub/config routes. Same class as F1.
4. `cloud-code/sessions/[id]/warm/route.ts` special-cases `svc:` only; review it against `requireHumanIdentity`.
