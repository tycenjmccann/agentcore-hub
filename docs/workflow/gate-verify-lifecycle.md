# Gate verification lifecycle (decision-bound human gates)

**Answer first.** A decision-bound human gate (a `human:*` ticket whose description declares `DECISION OPTIONS:`) closes only on a signed, single-use decision token. A token answers one ticket, one workflow and one review cycle. If the gate also carries a `postCondition`, an approved close is **held**: the gate stays In Review behind `gate:verifying` until the post-condition is observed. If the window ends first, the gate is marked `gate:approved-unverified` and the human is paged again. Nothing downstream unblocks while a gate is held. Every item of state below has one writer per twin, a defined reader, and a defined end of life. Both ticket twins (`lambda/agentcore-hub-tickets`, DynamoDB; `lambda/agentcore-hub-jira`, Jira) implement the same rules from the shared, byte-identical `gate-contract.mjs` and `decision-contract.mjs` (pinned by `scripts/check-fix-kinds-parity.sh`). The orchestrator owns none of this (DL-009).

Added by TEAM-5338 (review round 1 on TEAM-5315); the ledger, the hold claim, the cycle pins, the exit-based cut-off, the same-second staleness rule, the webhook's typed-gate rule, the lease-first release and the admin gate are TEAM-5347 (round 2). Related: DL-028 (conditional deploy gate) in `docs/architecture.md`.

## Lifecycle of one gate

1. **Create.** `create_issue` / `create_ticket` with `post_condition` (needs `human:*` and a `DECISION OPTIONS:` line).
2. **Decide.** The human picks an option in the hub console (the hub mints a token, only for a verified human, see [Who may decide](#who-may-decide)) or on Telegram (the bridge mints its own). The route forwards the token to `Tickets___transition_ticket`.
3. **Resolve.** `resolveDecision` (gate-contract) verifies the HMAC, ticket, workflow, expiry, the cycle cut-off (`notBeforeMs`) and that the jti is unspent.
4. **Spend + close or hold.** The jti is spent **atomically** — the DynamoDB twin in the same conditional write as the status, the Jira twin with one create-once S3 object (`IfNoneMatch:"*"`) in the ledger under `pipeline-artifacts/gate-decisions/`. Exactly one of two racing closes wins. With no post-condition, or one that is already met, the gate goes Done. Otherwise it is held: `gate:verifying` + a signed `gateVerify` record (`verifyUntil` = now + `VERIFY_WINDOW_MS`, 10 min). Every DynamoDB gate write is also pinned to the status and decision cycle it read; the Jira hold re-reads the status after its PUT and undoes itself if the gate moved.
5. **Reprobe** (`{mode:"reprobe"}`, EventBridge every 2 min). Each held gate is checked against the signed record. The Jira twin first **claims** the hold in the ledger (one actor per hold) and, after the Done POST, **verifies** from the changelog that the move was its own, compensating (back to the human's status, re-page) if not; the signed records are written only after that passes. **Met:** the gate goes Done (DynamoDB removes the record in the same write; Jira leaves the property inert behind its claim). **Window over and still unmet:** `gate:verifying` is swapped for `gate:approved-unverified` and the human is paged again.
6. **Reopen.** Any non-Done move out of In Review/Done (request changes, `blocked_by` park, a Jira-UI move) starts a new cycle — the ONE predicate is `isCycleResetMove` in `gate-contract.mjs`. Every earlier token and DECISION comment becomes stale (a token minted in the same second as the reset too), and the hold state is cleared.

## Who may decide

`src/lib/auth/human.ts` `requireHumanIdentity(req)` is the single answer. It is used by every hub route that mints a decision token or clears a DL-035 park. `requireHumanAdmin(req)` (TEAM-5347 F9) adds the `admin` group on top for operator actions — the CD registry (write access = deploy-trigger authority), the models registry and the GitHub App master credential — and `forbidden()` is the one 403 they answer (`error: "forbidden"`, `reason`). `isAdmin()` alone is never a gate any more: it is true for every caller under `AUTH_MODE=none`. It refuses:

- `unauthenticated`: auth is on and there are no identity headers.
- `default_identity`: `AUTH_MODE=none`, where every caller (agents with `http_request`/`shell` included) is `default` and headers are untrusted; or the user is literally `default`.
- `service_identity`: `svc:*`.

## Contract change for the frontend ticket (held response)

`POST /api/workflow/[id]/tickets/transition` now returns a distinct 200 body when the twin holds an approved close (type `TransitionHeldResponse`, `src/lib/workflow/decision-grammar.ts`, re-exported from `decision-contract.ts`):

```json
{ "success": true, "held": true, "status": "verifying", "ticketId": "TEAM-G", "targetStatus": "done",
  "newStatus": "in_review", "verifyUntil": "2026-10-06T12:30:00.000Z",
  "postCondition": { "met": false, "detail": "lambda_version: want 7, have 6" },
  "decision": "continue", "completionRecordWritten": true }
```

`decision` appears only when a decision was picked; `completionRecordWritten` only when `evidence` was sent. Every other success keeps the old shape (`{success, ticketId, newStatus: targetStatus, …}`).

**Frontend follow-up — done (TEAM-5339).** `src/components/workflow/TicketDetailModal.tsx` now parses the response through `src/lib/workflow/transition-result.ts` (`parseTransitionResponse`) instead of repainting `targetStatus` on any `res.ok`: a held response keeps the ticket `in_review` and shows "Approval held — verifying post-condition…" with `postCondition.detail`; the ticket's own `gate:verifying` / `gate:approved-unverified` labels (`gateHoldState`) drive the same banners on load, so reopening the modal never shows stale state, and an approved-unverified gate re-pages through the existing decision picker (Approve relabelled "Override (unverified)"). Still open: the 403 refusal still shows the same "service" notice regardless of `identity` — `detail === "decision_channel_unavailable"` + `identity: "unauthenticated"` / `"default_identity"` should instead say "sign in through SSO or use Telegram". The Telegram bridge (`deploy/telegram-bug-intake/index.mjs`, gate ✅ and DECISION callbacks) already branches on `status === "verifying"`.

## Residual risks (accepted, bounded)

TEAM-5347 closed round 1's R1 (the Jira jti window: the spend is now a create-once S3 object, atomic) and R4 (an unbound gate passing through on `/myself` failure: a typed gate is never unbound, and no actor fails closed too). What remains:

- **R1: direct table/property writes.** The guarantees assume the only writers are the twins' Lambda roles. A principal with direct `dynamodb:UpdateItem` on the tickets table, or Jira admin credentials, could strip `decisionJtisUsed` or the `gateCycleResetAt` stamp. It still cannot forge a token or a `gateVerify` signature (the HMAC key is in Secrets Manager), and it cannot remove a ledger object without `s3:DeleteObject` on `pipeline-artifacts/gate-decisions/*`, which no hub principal holds. The fleet is meant to reach tickets only through the `Tickets___*` tools (`TICKET_TOOLS_LAMBDA`). Any runtime or operator role that also holds direct write on the tickets table sits inside this residual, and should be audited in the follow-up IAM review.
- **R2: `/myself` down or actor unknown → reopen cost** (`src/app/api/jira/webhook/route.ts`). When the service account cannot be resolved, or the webhook payload carries no `user`, a human Jira-UI Done on a decision-bound **or typed** gate is not ratified. It is reopened and paged again (throttled to once per gate per 10 min, per ECS task, and only once a page has actually landed). A real human approval made in the Jira UI during an outage therefore costs one more click. Only a plain gate that declares no options and carries no gate kind passes through.
- **R3: the Jira compensating reopen.** Jira has no conditional transition, so a human reopen landing between `liveHold` and the Done POST is detected after the fact (`verifyOwnDone`) and undone (`superseded_compensated`): for the few seconds in between the issue reads Done, though no signed record exists and nothing downstream (pipeline-tools, workflow-output) trusts a Done without one. The compensating move itself is a reset exit, so the human decides again.
- **R4: rollout.** Tokens without a jti, `gateVerify` v1 records, and holds whose jti is only in the mirror property (the property fallback is removed next release) fail closed or are accepted exactly as documented in the state table. The human decides again: at most one extra click per in-flight gate.
